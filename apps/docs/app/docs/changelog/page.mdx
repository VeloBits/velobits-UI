# Changelog

Versions are cut with [changesets](https://github.com/changesets/changesets); the
authoritative per-package history lives in each package's `CHANGELOG.md`. This
page is the summary worth reading.

## Unreleased

### Documentation and build

The docs site and the registry are now **one build and one origin**. `npm run
build` produces a single static export containing both the pages you are reading
and the `/r/*.json` the shadcn CLI fetches, so there is no arrangement in which
one is stale relative to the other, previously the registry compile was a
separate command that CI happened to run as its own step.

- **A page per registry item.** Generated from `registry/registry.ts`, so a new
  component gets documentation with no further edit. Each carries its install
  command, its dependencies, and a prop table.
- **Prop tables are extracted from the TypeScript sources** at build time rather
  than written by hand. A hand-written table for 38 components is 38 places for
  the documentation to disagree with the code, silently.
- **`@velobits` namespace.** `npx shadcn@latest add @velobits/button` now works
  once the registry is in your `components.json`. The full-URL form still works
  everywhere and is not going away. See [Registry](/docs/registry).
- **Syntax highlighting at build time**, so no highlighter ships to the browser.
- **⌘K search** across every page, built on the system's own `CommandPalette`.

### Components

- **`Motion` added**, `PageTransition`, `Stagger`, `StaggerItem` and `FadeIn`,
  on the `framer-motion` peer that was already required and until now bought
  nothing but `MotionConfig`. Subpath-only, like `Form`: nobody should download
  Framer's runtime to render a `Button`. See [Motion](/docs/components/motion).

## 0.1.0

Initial release. 37 components on the shared token layer, authored once in the
registry source and shipped both as npm packages and as a shadcn registry, with a
parity test asserting the two never drift.

- **Tier 1, 18 primitives.** `Alert` `Avatar` `Badge` `Button` `Card`
  `Checkbox` `Field` `GlassSurface` `Input` `Kbd` `Label` `NativeSelect`
  `Separator` `Skeleton` `Spinner` `Switch` `Textarea` `Tooltip`
- **Tier 2, 6 overlays.** `CommandPalette` `Dialog` `DropdownMenu` `Popover`
  `SidePanel` `Toast`
- **Tier 3, 13 composites.** `Accordion` `AppShell` `Breadcrumb` `CodeBlock`
  `DataTable` `DiffViewer` `EmptyState` `Form` `Pagination` `SegmentedControl`
  `StatusChip` `Table` `Tabs`
- Plus `cn`, `VelobitsProvider`, `useTheme`, `useMediaQuery` and
  `useRowSelection`. Dual ESM/CJS with per-condition types; every component also
  has its own subpath entry.

### Decisions worth knowing about

- **`Form` is subpath-only**, `@velobitsio/ui/form`, never the barrel.
  `react-hook-form` is an optional peer and the barrel is a single bundled
  module, so re-exporting it would put a top-level `import 'react-hook-form'`
  into `dist/index.js` and break every consumer without forms. Bundling our own
  copy would be worse and quieter: separate module state means
  `useFormContext()` reads a different context from your `useForm()`.
- **`DataTable` is a column registry, not TanStack.** No VeloBits surface
  pivots, groups or resizes columns, and adopting TanStack would cost roughly
  14 kB for none of it. A surface that ever needs virtualisation should use
  TanStack directly on `Table`.
- **`EmptyState` defaults to `surface="none"`** even though `Table` and
  `Accordion` default to glass, its documented homes are a table body and a
  card body, both already glass, and defaulting it would ship nested glass at its
  commonest call site.
